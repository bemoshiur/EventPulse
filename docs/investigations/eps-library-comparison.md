# EPS Library Comparison — Sprint 3 Day 21 Decision

**Date:** 2026-05-19 · **Author:** Claude Code (Day 20 AM Block 2 background research) · **Decision lock:** Sprint 3 Day 21

## 1. Existence Check

- **`eps-gateway-nodejs` on npm:** EXISTS. v1.0.0 published 2026-01-17 by `imtiaznajim`. Single version. Source: [npm registry](https://registry.npmjs.org/eps-gateway-nodejs).
- **`EPS-PG/EPS_Nodejs` on GitHub:** EXISTS. Created 2026-02-09, owned by `EPS-PG` org (verified-to-be the official EPS account per its bio "Libraries, SDKs, and sample code for integrating the EPS Payment Gateway", blog `eps.com.bd`, email `integration@eps.com.bd`). Source: [github.com/EPS-PG/EPS_Nodejs](https://github.com/EPS-PG/EPS_Nodejs).

**Critical finding (unprompted):** The EPS-PG `EPS_Nodejs` repository is a **byte-for-byte clone** of Imtiaz Najim's `imtiaznajim/eps-gateway-nodejs`. Evidence: the EPS-PG `package.json` still declares `"name": "eps-gateway-nodejs"` and `"repository.url": "https://github.com/imtiaznajim/eps-gateway-nodejs.git"`. README, src/EPS.ts, tests, and tsconfig are identical. EPS-PG appears to have vendored the community SDK three weeks after it was published, without authoring their own. **Both "candidates" are effectively the same code.**

## 3. Recommendation: Build a Thin In-House Wrapper. Do NOT Depend on Either Library.

**Both libraries fail the quality bar for a payment-processing dependency.** Top three reasons:

1. **Both are the same code, both single-author, both effectively unmaintained.** The "official" EPS-PG repo is a 2-commit bulk upload of Imtiaz Najim's SDK without re-authorship — same package name, same repo URL in `package.json`, same one test file. There is no team behind either; there is no release cadence; there is no semver story. EPS-PG has 7 sibling repos (PHP, Laravel, WHMCS, ASP.NET, Flutter), all pushed in a single late-Jan/early-Feb 2026 burst — this looks like a procurement-driven dump, not an actively-maintained product line.

2. **The status-alias gotcha (CLAUDE.md §11.4) is not handled.** The SDK exposes raw `Status: 'Success' | 'Failed' | 'Pending'` and the README never mentions `COMPLETED`, `CANCEL`, `CANCELLED`, `CANCELED`. CLAUDE.md §11.4 explicitly calls these out as field aliases we've hit. We'd have to wrap `verifyPayment()` with our own `normaliseStatus()` anyway — at which point the SDK provides only an axios wrapper and a 6-line HMACSHA512 helper.

3. **Single-author + zero adoption + payment-critical = unacceptable supply-chain risk.** 135 npm downloads/month (mostly bots), zero stars, zero issues filed, single-developer surface. Per immutable rule R2 ("money never lies") and our auth-library lesson (§5.3, Lucia in maintenance mode → we composed our own), we already have project precedent for rejecting unmaintained dependencies on the most security-critical surfaces. EPS integration is in the same tier as auth.

**Proposed shape (`apps/api/src/infra/eps/`):**

- `client.ts` — axios instance, base-URL switch (`pgapi.eps.com.bd` vs sandbox), `getToken()` with Redis TTL cache, HMACSHA512 via `@noble/hashes` (already a dep per §5.3 — zero new deps).
- `init.ts` · `verify.ts` — typed wrappers around `InitializeEPS` + `CheckMerchantTransactionStatus`, returning zod-validated responses.
- `normalise-status.ts` — the alias-collapsing shim §11.4 demands, with explicit unit tests for all 8 alias variants.
- `types.ts` — hand-written from the EPS V5 docs (the SDK's types are already hand-written too; we copy the shape, drop the SDK).
- ~400 LOC total. Estimated 1.5 days vs the lifelong dependency-monitoring cost of the SDK.

**Fallback if time pressure forces an SDK pick:** use `eps-gateway-nodejs` from npm (not the EPS-PG fork — the npm package gets security patches if Imtiaz ever ships them; the GitHub fork is frozen). Wrap it behind our own adapter so a future migration to in-house is a one-file change. But the right answer is to skip the SDK.

**This mirrors §5.3's Lucia decision.** Same rationale, same outcome.
